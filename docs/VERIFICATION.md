## Methods

| Method | What it proves |
|---|---|
| **Minecraft 26.3's own DataFixer** | Every Java output (chunks, `entities/`, `level.dat`, players) is upgraded by the game's DataFixer code, run outside the game by a harness built from the decompiled 26.3 client. A chunk that fails is one Minecraft would discard and regenerate. |
| **Generator harness** | For each Minecraft version, a harness loads the game jar and calls the game's own terrain generator with a given seed, without starting the game. WorldBridge's generator must give the same blocks. |
| **Reference worlds** | New worlds generated by each game version with a fixed seed and a few hundred chunks explored, compared column by column with WorldBridge's generator. Differences must fall in the game's decoration (trees, ores, lakes, dungeons, mineshafts). |
| **cubiomes** | Biome stacks compared with [cubiomes](https://github.com/Cubitect/cubiomes) on several seeds, including Large Biomes. |
| **Game source code** | LCE formats are implemented from the 4J source (`Minecraft.World`), and neoLegacy's generator, item, enchantment and entity tables from neoLegacy's source. Storage codecs are tested against a literal Python port of the C++. |
| **Strict old-NBT reader** | Alpha and Beta outputs are read back by an NBT reader with the same rules as those games (tag types 1–10 only, fixed field types). |
| **Round trip** | Each conversion is converted again to Java 1.12 and inspected: chunks per dimension, blocks, chest contents, sign text, block entities, entities, player. |
| **Bit-identical output** | Multi-core conversions are compared byte for byte with single-core ones. |
| **`tools/seamcheck.py`** | Measures, for each pair of neighbouring columns (converted, ring, game), the height jump of the ground and every spot where water leaks. |

Game jars and decompiled code are used only to read and to verify. They are never included in
WorldBridge.

## Conversion matrix

`tools/matrix.py` builds a sample world with everything converters usually break:

- **Containers:** a named double chest, a burning furnace, a dispenser, a hopper, a dropper, a full
  red shulker box, an ender chest, a jukebox with a disc and a spawner.
- **Items:** a named enchanted sword, a written book, a potion, dyed leather armour and full
  stacks.
- **Blocks:** a sign with accents and €, a bed, a patterned banner, a flower pot, heads, redstone,
  doors, stairs, slabs, fences, panes, trapdoors, rails and 1.8–1.12 blocks.
- **Entities:** a sitting tamed wolf, a saddled armoured horse, a villager, a saddled pig, a named
  armoured zombie, an item frame with a map, a painting, an armour stand, minecarts, a boat and a
  dropped item.
- **Player:** armour, ender chest and experience.
- **World:** three dimensions, negative coordinates and chunks 16,000 blocks away.

It writes that world in every source format, converts each one to every target, and checks each
result.

| Run | Result |
|---|---|
| Full matrix: 18 sources × 17 targets = 306 pairs | 289 / 289 conversions succeeded; 17 pairs not applicable (Better than Adventure converts only to Java 26.3) |
| Every Java output through the 26.3 DataFixer (81 outputs) | 0 chunks rejected |
| Robustness: random bytes in a chunk, a truncated region file, a 100-byte region file, no `level.dat`, paths with spaces / accents / € / Japanese, `.zip` sources, a non-empty output folder, cancellation halfway | every case ends cleanly: bad chunks are skipped with a warning, errors are clear, no temporary folders are left behind |

conversions identical bit for bit, and the 2 that go through Amulet identical in content (Amulet
changes random UUIDs on every run).

| Conversion | Before | After |
|---|---:|---:|
| Java 26.3 → LCE Windows64, with the ring (1,252 chunks) | 130 s | 46 s |
| Java 26.3 → Java 1.12 with the ring | 129 s | 52 s |
| Java 26.3 → Java 1.16 (Amulet) | 88 s | 35 s |
| Java 1.12 → LCE Windows64, with the ring (5,678 chunks) | 156 s | 55 s |
| Java 1.12 → Beta 1.7 with the ring and compressed mountains | 177 s | 85 s |
| Java 1.12, 700 chunks moved and biomes painted → LCE | 123 s | 36 s |
| LCE Windows64 → Java (upgraded by the game, 8,179 chunks) | 28 s | 7 s |
| LCE Windows64 → Java 1.12 with the ring | 172 s | 75 s |
| Alpha → Java 1.12 with the ring (7,502 chunks) | 194 s | 94 s |
| Bedrock → LCE Windows64 with the ring | 225 s | 114 s |
| PS Vita → LCE PS4 | 3.6 s | 1.2 s |
| Java 1.12 → Bedrock (Amulet, single core) | 64 s | 63 s |

All 18 test conversions: 27.6 → 12.2 minutes. On a single core, the neoLegacy generator became
39 % faster and the 1.7–1.12 generator 51 % faster. The map preview loads 2–2.5 times faster.

What the measure found and changed (fixes 58–64 in [FIX_HISTORY.md](FIX_HISTORY.md)):

| | Before | After |
|---|---:|---:|
| 998,784 chunks → Java 26.3: time, memory | 8 min 30 s, 1.39 GB | 7 min, 0.63 GB |
| 998,784 chunks → LCE: time, memory | 6 min 30 s, 1.37 GB | 2 min, 0.5 GB |
| 249,696 chunks → Bedrock: time, memory | 29 min 25 s, 2.96 GB | 15 min 45 s, 0.66 GB |
| Bedrock → Java, 98,304 chunks on 4 cores | hung | 2 min 50 s |

The memory no longer grows with the number of chunks in the steps that held one entry per chunk
(the chunk index, the biome filler, the Bedrock height maps); what still grows is one small entry
per chunk in the lists of chunks to convert. The disk a conversion needs is the output plus, for the
routes through the numeric hub (LCE and old formats → Bedrock or Java 1.13+), a copy of the hub;
working copies of Bedrock and Java 1.13+ sources are hard links, not copies.
